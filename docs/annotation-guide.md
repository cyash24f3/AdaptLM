# Annotation specification 1.0

This is an authored, fictional English support track. Inputs were authored by the implementation AI; scenario expansions and labels were generated by deterministic code. **No labels are human-reviewed.** Rule-consistent outputs are not established real-world truth. `review-queue.csv` is an empty human review workflow, not evidence of completed reviews.

## Category boundaries

| Primary issue | Meaning | Boundary / counterexample |
|---|---|---|
| duplicate_charge | One purchase or renewal charged twice | An explicit refund request for the extra charge retains this issue. A single regretted purchase is refund_request. |
| refund_request | Customer asks to return money for one purchase | Never infer eligibility or approval. |
| cancellation_request | Stop future membership/service renewal | Does not imply repayment for the current period. |
| delivery_problem | Shipment late, missing, incomplete, or misdelivered | An arrived but broken item is damaged_item. |
| damaged_item | Explicit physical damage to a delivered product | Setup confusion alone is product_help. |
| account_access | Login, password recovery, verification, lockout | Subscription cancellation alone is not account_access. |
| product_help | Setup, operation, maintenance, product instructions | No support policies or actual instruction answers are generated. |
| other_support | Customer requests support but details do not fit the categories | General non-support questions are out_of_scope. |

Choose an explicitly requested main issue. A request to refund a second charge has the documented duplicate-charge precedence. Equal unrelated issues, uncertainty about which issue exists, or no discernible primary issue use `primary_issue=null`, `needs_clarification`, and an `issue_details` question. Secondary issues are not part of v1. Do not invent a priority.

## Required operator details

Duplicate charge and refund require email and transaction ID; cancellation requires email and plan name; delivery and damage require order ID; account access requires email; product help requires product name; other support requires issue details. These are a published illustrative operator contract, not a real company's policy. Clear classification plus missing details is `needs_clarification` with the category retained. All required details present means `triaged`. Out-of-scope has a null category and no operational questions.

## Evidence and entities

Offsets are zero-based Python Unicode code points, with exclusive end, into the exact original message. JavaScript uses `Array.from` before highlighting. Emojis and combining marks are preserved; a grapheme may contain several code points. Repeat occurrences have distinct spans. Raw values equal span text. No date/amount/identity normalization is performed. Relative dates stay relative; reference timestamps are null. Use only order_id, transaction_id, email, product_name, plan_name, amount, currency, date_expression when stated. Fictional emails end in example.invalid.

For amounts, the numeric amount and `$` currency are separate exact spans. Names and plans are limited to a documented authored vocabulary in the generator; regex extraction is not a general semantic extractor. Negative phrases such as “no transaction ID” do not create an ID entity. No unstated refund status, amount, identity, or policy fact is permitted.

Summaries should preserve the main issue and qualifiers, cite exact spans, and stay short. Reference summaries are verbatim scenario sentences. A predicted paraphrase may be acceptable even when exact reference agreement fails. The span checker cannot decide whether a cited quote supports a paraphrase or whether a selected passage is the important fact.

## Semantic review rubric

Score each category/claim/record: 0 wrong or unsupported; 1 partly correct or missing a material qualifier; 2 correct with required facts and no unsupported addition. For each summary claim mark supported (all facts follow from cited text), unsupported (an added fact contradicts or exceeds evidence), or ambiguous (evidence insufficient to resolve). Assess preservation of relevant negation, timing, and scope separately. A verbatim but irrelevant sentence may be factually supported and still an incomplete summary.

“Charged twice” does not support “refund approved.” A valid existing span does not establish the right entity type. A null category may be acceptable for genuinely equally weighted issues. No string metric is presented as a semantic judge. Automated outputs and human reviews must use different provenance records; reviewer role, timestamp, changes, and observed disagreement are required before changing review status.

The queue samples ordinary and injection variants across every family and split. Human reviewers should work without model predictions first, then adjudicate disagreements. There is no agreement percentage until actual independent reviewers submit records.
